VERIFICATION METHOD
--------------------
- Every backend route was checked with `node --check` (syntax) and,
  where listed, has an automated integration test in backend/tests/
  (Node's built-in test runner, `node --test`), run against a live
  `docker compose up` stack.
- Every frontend file was checked with `npx tsc --noEmit` (type
  correctness). Frontend behavior for T1/T2 features was verified by
  reading the component against its API calls; it has not been
  exercised through an actual browser session by an automated E2E test.
- KNOWN LIMITATION: nothing in this report was verified by an automated
  end-to-end run of `docker compose up --build` performed by the AI
  assistant that did this work — that tool had no Docker access in its
  environment. A human must run the full stack at least once before
  trusting this report completely.

TIER 2 — JUDGING
==================

[PASS] Judge invitation and assignment
  - Judge/organizer accounts: admin-only POST /api/users (never
    self-registered — signup always creates a participant). Real
    frontend: RealUserManagement.tsx at /admin (admin role only)
  - Exactly one admin account, enforced by a database-level partial
    unique index (one_admin_only), not just API logic
  - Assignment: POST /api/judging/assign, round-robin with a rotating
    cursor for load balancing, idempotent (ON CONFLICT DO NOTHING)
  - Test: users.test.js (6 tests: create judge/organizer, reject
    non-admin, reject a second admin, reject duplicate email, list/filter)
  - Test: judging.test.js "assign: judges are assigned round-robin
    across submissions"

[PASS] Weighted, configurable judging rubrics
  - POST /api/judging/rubric (organizer/admin, replaces the event's
    full criteria list, validates weights sum to 100)
  - Real frontend: rubric editor embedded in RealJudgingOps.tsx
    (add/remove/edit criteria, live running total vs. 100, explicit
    warning that saving replaces the rubric and can delete existing
    scores for removed criteria)
  - Guard: an event with zero rubric criteria cannot have judges
    assigned to it (400, "no rubric criteria yet"), and
    /assignments/:id/complete independently re-checks the same
    condition, so a judge can never "complete" a review with nothing
    to actually score
  - Test: judging.test.js "rubric: seeded event has 4 criteria summing
    to weight 100"; new test "assign: refuses to assign judges to an
    event with no rubric configured"

[PASS] Backend-enforced role isolation
  - A judge can only read/write their own assignments
    (assignment.judge_id === req.user.id checked on every judging route)
  - Test: judging.test.js ownership-isolation test — a second real
    judge is created via direct SQL, and the seeded judge is confirmed
    to get 403 trying to score the second judge's assignment

[PASS] Judge progress dashboards
  - GET /api/judging/my-assignments — a judge's own assignments only
  - Real frontend: RealJudgeDashboard.tsx (progress meter, next action)

[PASS] Cross-judge score normalization

    zero variance falls back to their raw weighted score for that one
    contribution (not silently zeroed), and the result is flagged
    fully_normalized: false so a partially-raw ranking is visible
    rather than blended in unmarked
  - Full methodology: JUDGING.md
  - Test: judging.test.js "results: normalized results are computed..."

[PASS] CSV export throughout the workflow
  - GET /api/judging/export.csv?event_id=&type=results|assignments|scores
  - Frontend downloads with the auth header attached (a plain <a href>

TIER 3 — PUBLIC
================

[PASS] Configurable community voting

  - One vote per (submission, voter), enforced by a DATABASE unique
    constraint (votes.submission_id, votes.voter_id) — not just an API

  - Voting excludes drafts and the caller's own team's submission
  - Real frontend: RealVotingBoard.tsx at /voting
  - Test: voting.test.js "participant can vote once, a second vote on
    the same project is rejected as duplicate"; "cannot vote for your
    own team's submission"

[PASS] Comments
  - GET/POST /api/voting/:id/comments, any authenticated role, 2000
    char cap, append-only (no edit/delete endpoint)
  - Real frontend: inline comment thread per project on /voting
  - Test: voting.test.js "any authenticated role can post and read"

[PASS] Hidden results during voting
  - events.results_published (default false) gates GET
    /api/voting/results for non-staff callers (403 until published);
    organizer/admin can always preview. POST /api/voting/publish
    (organizer/admin) flips the flag
  - Real frontend: Results page shows a Publish/Unpublish control for
    staff and a "results not published yet" state for participants
  - Test: voting.test.js "results: hidden from participants until an
    organizer publishes them"

[PASS] Randomized project ordering
  - GET /api/voting/feed uses ORDER BY random() — re-shuffled on every
    request, so no submission is systematically favored by list
    position (a fixed per-viewer seed would be a further refinement;
    see THREAT_MODEL.md)

[PASS] Rate limiting
  - Per-voter limit: no more than 10 votes per rolling 60-second
    window (checked server-side against votes.created_at before every
    insert); a request over the limit gets 429 and is written to the
    audit log as RATE_LIMIT_TRIGGERED

[PARTIAL] Duplicate detection
  - Duplicate VOTES (same voter, same project) are fully prevented at
    the database level. Duplicate/Sybil ACCOUNTS (one person creating
    many participant accounts to vote multiple times) are NOT detected
    — there is no email verification, device fingerprinting, or IP
    correlation in this build. Documented as a known gap and threat in
    THREAT_MODEL.md rather than silently left out.

[PASS] Audit trails
  - Append-only audit_log table; written on vote cast, vote rejected
    (duplicate), rate limit triggered, comment posted, judge assigned,
    account created, results published/unpublished
  - GET /api/audit (organizer/admin only)
  - Real frontend: RealAuditLog.tsx at /audit
  - Test: voting.test.js "audit log: organizer/admin only, records a
    vote and a rejected duplicate"

DELIBERATE DESIGN DECISIONS WORTH NOTING
===========================================
- Exactly one admin account, enforced at the database level (partial
  unique index), not just application logic.
- Not even an admin can submit or edit a score on a judge's behalf —
  ownership of a score is judge-only, by design (see JUDGING.md).
- Replacing an event's rubric deletes scores tied to removed criteria
  (ON DELETE CASCADE) — a deliberate simplicity trade-off, surfaced to
  the organizer as an explicit warning in the UI rather than hidden.
- Voting and judging are deliberately independent signals: judges and
  organizers cannot vote (role isolation), and normalized judging scores
  and community vote counts are never combined into a single number —
  both are shown side by side on Results and left for a human to weigh.
- The integration test suite runs real HTTP requests against whatever
  database the backend is pointed at (there's no separate throwaway test
  database in the default docker-compose setup), so running `npm test`
  will add real teams/submissions/votes alongside the fixture data. Run
  `npm run reset` (truncates all tables, re-seeds) before a demo or a
  judging session to get back to a clean, fixture-only state.
